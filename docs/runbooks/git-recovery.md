# Runbook: восстановление истории Git

Назначение: шпаргалка для выбора правильной команды, когда нужно откатить,
перестроить или найти коммит в репозитории `release-board`. Не заменяет
документацию Git, а фиксирует принятые в проекте решения и ограничения.

Стек: Git `2.53.0`, основной репозиторий `git@github.com:Slon4ek/release-board.git`,
`main` защищён Rulesets: блок force-push, блок удаления, squash-merge только.

## 2. Подробности

### 2.1 `git revert <sha>`

Используется, когда нужно **отменить изменения уже опубликованного коммита**
без переписывания истории. Создаёт коммит с обратным диффом. Если между
опубликованным коммитом и текущим HEAD есть другие изменения, revert может
потребовать разрешения конфликта — в этом случае ведёт себя как merge.

```bash
git revert 0538926 --no-edit
make test
git push
```

**Ограничения:** не подходит, если нужно **удалить** коммит из истории
(например, залит секрет). Для этого — revert + новый коммит, удаляющий
секреты явно: история остаётся, но в HEAD секрета нет.

### 2.2 `git reset --hard <target>`

Перемещает указатель ветки и **сбрасывает** индекс и рабочее дерево к `<target>`.
Используется локально, когда нужно «откатить» набор неопубликованных коммитов
обратно на эталонный коммит (`HEAD~N`, sha или `origin/main`).

```bash
git reset --hard HEAD~1
```

**Ограничения:** после `reset --hard` коммиты между старым HEAD и target
становятся недостижимы для обычного `git log`. Доступны через `reflog`,
пока не истёк срок (по умолчанию 90 дней). На опубликованных ветках не
применяется — нужен `git revert`. На `main` запрещён Rulesets.

### 2.3 `git restore <file>`

Откатывает незакоммиченные изменения файла(ов): без флага — рабочее дерево
из HEAD, `--staged` — индекс из HEAD (отменяет `git add`).

```bash
git restore docs/report.md                # файл из HEAD
git restore --staged src/api/health.py    # индекс из HEAD
```

**Ограничения:** не трогает коммиты. Если нужно откатить закоммиченное —
`revert` (опубликованное) или `reset` (локальное).

### 2.4 `reflog`

Локальный журнал перемещений HEAD. Каждая операция, меняющая HEAD
(`commit`, `checkout`, `reset`, `rebase`, `merge`) создаёт запись.
Записи хранятся ~90 дней (`gc.reflogExpire`), недостижимые коммиты — ~30
дней (`gc.reflogExpireUnreachable`).

```bash
git reflog -10
# 49ab4f7 HEAD@{0}: reset: moving to HEAD~1   ← куда упал указатель
# 1598f51 HEAD@{1}: commit: ...               ← состояние ДО отката
git switch -c feature/reflog-restore 49ab4f7
```

**Что искать:** строка с описанием `reset:` показывает новое положение
указателя; **соседняя, более ранняя** запись `HEAD@{N}` хранит состояние до
отката — её sha и есть потерянный коммит.

**Ограничения:** reflog **локальный** — в `origin` не пушится, на другом
клоне недоступен. Страховка от локальных ошибок, а не от удалённых.

### 2.5 `git cherry-pick <sha>`

Переносит изменения одного коммита на другую ветку как **новый** коммит.
Полезен для forward-port фиксов: исправление сделано на линии поддержки,
нужно перенести на актуальный `main`.

```bash
git cherry-pick 49ab4f7
git log --oneline -2          # новый SHA ≠ 49ab4f7 — доказательство копии
git show --stat HEAD          # те же правки
make test                     # регрессий нет
git push
```

**Ограничения:** конфликт возможен, если строка из коммита X изменилась в
целевой ветке. Разрешается как при merge: правка → `git add` →
`git cherry-pick --continue`. Флаг `-x` добавляет в сообщение метку
`(cherry picked from ...)` — след маршрута, в публичном репозитории
использовать сознательно.

### 2.6 `git rebase <base>`

Перестраивает историю: берёт коммиты ветки, которых нет в `<base>`, и
переигрывает их сверху `<base>` по одному. Позволяет убрать мусорные
коммиты, объединить (squash/fixup), изменить порядок или сообщения.

```bash
git rebase -i HEAD~3          # интерактивный todo-лист (нужен редактор)
git rebase origin/main        # переклеить на актуальный main
git push --force-with-lease   # если ветка уже опубликована
```

**Ограничения:** пересоздаёт коммиты (новые SHA). Пока истории расходятся,
push требует `--force-with-lease`; когда родитель уже на сервере — обычный
fast-forward. На `main` rebase невозможен: Rulesets блокируют force push,
историю `main` меняет только squash-merge через PR.

**Конфликт при rebase:** Git останавливается на маркерах
`<<<<<<<`/`=======`/`>>>>>>>`. Стороны в rebase **инвертированы** относительно
merge: HEAD — это `<base>` (чужая ветка), а переклеиваемый коммит — «свой».
Если разрулить, оставив версию HEAD, коммит станет **пустым** и будет
пропущен (`--skip`) — тихая потеря работы. Надёжный способ: заменить весь
диапазон маркеров одной строкой механически:

```bash
sed -i '/^<<<<<<< HEAD$/,/^>>>>>>> /c\<итоговая строка>' README.md
grep -c '<<<<<<<' README.md   # 0 — маркеров нет
git add <файл>
git rebase --continue
```

Если после `rebase --continue` Git сообщает «коммит пустой» — разруление
выбрало не ту сторону: посмотрите `git status`, правьте заново.

## 3. Что выбирать

| Ситуация | Рекомендация |
| --- | --- |
| Коммит уже в `main` или другой опубликованной ветке, нужно отменить | `git revert` |
| Локальная ветка, нужно откатить/переупорядочить коммиты | `git reset` / `git rebase -i` |
| Незакоммиченные правки файлов — испортил, надо вернуть | `git restore` |
| Потерял коммит после `reset`/`rebase` | `git reflog` → `git switch -c <name> <sha>` |
| Нужно перенести один коммит на другую ветку | `git cherry-pick` |
| Нужно перестроить локальную ветку на актуальный `main` | `git rebase origin/main` + `--force-with-lease` |
| Нужно найти, какой коммит сломал тест | `git bisect run <тест>` |

## 5. Дополнительно: `git bisect`

Не входит в обязательный список (ТЗ, строка 178), но полезен для поиска
регрессии в длинной цепочке.

```bash
git bisect start
git bisect bad HEAD
git bisect good <good-sha>
git bisect run <команда, 0 = хорошо, 1 = плохо>
git bisect reset
```

Требует воспроизводимый тест, возвращающий 0/1. `git bisect skip` — если
коммит не тестируем (например, пустой merge).

В этом проекте: `test_planned_cannot_rollback` — юнит без БД, подходит для
`run`. Нашёл `a44845f` за 2 проверки из 4 возможных (`log₂4 = 2`).

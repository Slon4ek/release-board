# Участие в проекте

Правила работы с репозиторием release-board: стратегия веток, формат commit,
обязательные проверки и порядок оформления изменений.

## Стратегия веток

Используется GitHub Flow: `main` хранит рабочее состояние, каждое изменение
проходит через короткую ветку и pull request. Ветка `develop` не нужна.

| Ветка | Откуда создается | Куда сливается | Срок жизни |
| --- | --- | --- | --- |
| `main` | начальная ветка | не сливается в другую ветку | весь проект |
| `feature/<topic>` | свежий `main` | `main` | до слияния задачи |
| `fix/<topic>` | свежий `main` | `main` | до слияния исправления |
| `release/1.1` | тег `v1.1.0` | отдельная линия поддержки | пока поддерживается 1.1.x |
| `hotfix/1.1.1` | `release/1.1` | `release/1.1` | до выпуска `v1.1.1` |

`release/1.1` и `hotfix/*` относятся к упражнению по поддержке старой версии
и в обычный порядок работы не входят.

## Правила обновления ветки

1. Обнови локальный `main` перед началом работы:

   ```bash
   git fetch
   git pull --ff-only
   ```

   `--ff-only` не даст pull'у создать merge-коммит или переписать историю:
   при расхождении веток команда откажет, и конфликт решается явно.

2. Создавай рабочую ветку только от свежего `main`:

   ```bash
   git switch -c feature/<topic> main
   ```

   Для исправления — `fix/<topic>`.

3. Один commit — одно изменение или один рефакторинг. Код и тесты на него
   коммитятся вместе.

4. Отправь ветку и открой PR:

   ```bash
   git push -u origin <ветка>
   ```

5. Дождись зелёного CI и сделай squash merge: один PR оставляет один связный
   commit в `main`.

6. Удали ветку после слияния:

   ```bash
   git push origin --delete <ветка>
   git branch -d <ветка>
   git fetch --prune
   ```

## Формат commit

Conventional Commits, тип по-английски, описание по-русски:

```text
<type>: <описание>
```

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность |
| `fix` | исправление ошибки |
| `docs` | только документация |
| `test` | только тесты |
| `refactor` | рефакторинг без изменения поведения |
| `ci` | настройки pipeline |
| `chore` | инфраструктура, зависимости, конфигурация |
| `build` | сборка и связанные инструменты |

Описание начинается с сути изменения, без точки в конце. Номер PR вручную
не добавляется — он появляется автоматически при squash merge.

Примеры из истории:

- `feat: модель Release, схемы и начальная миграция`
- `fix: передавать pyright абсолютный путь интерпретатора`
- `docs: актуализировать отчёт и окружение под разделение lock-файлов`

## Обязательные проверки

Перед отправкой ветки:

```bash
make check
```

`make check` выполняет последовательно:

| Шаг | Команда | Что проверяет |
| --- | --- | --- |
| Lint | `make lint` | Ruff: стиль и формат, без правок файлов |
| Typecheck | `make typecheck` | pyright в strict-режиме |
| Test | `make test` | pytest: валидация, API, readiness, миграции |

Тесты идут на отдельной базе `release_board_test`. Для их запуска из чистого
клона нужны `cp .env-test.example .env-test` и `make test-db`.

В CI job `check` (`.github/workflows/ci.yml`) выполняет те же три шага на
каждый PR — сервис PostgreSQL 16, переменные `MODE=TEST` и
`DB_NAME=release_board_test`. Слияние возможно только после зелёного `check`.

## Защита ветки main

`main` защищён GitHub Rulesets, Enforcement `Active`:

- прямые push запрещены — изменения идут только через PR;
- разрешён единственный метод слияния — squash merge;
- PR обязан пройти обязательную проверку `check` и быть up to date;
- удаление ветки и force push запрещены;
- обязательное одобрение не включено: проект ведётся в одиночку.

**Опубликованную историю `main` не переписывать.** Запрещены
`git push --force`, `git reset --hard` и `rebase` поверх опубликованных
коммитов. Ошибочный коммит отменяется только через `git revert` — новым
коммитом, добавляющим обратное изменение в историю.

## Оформление pull request

Каждое изменение — один PR из `feature/*` или `fix/*` в `main`. Описание
заполняется по шаблону `.github/PULL_REQUEST_TEMPLATE.md` — GitHub подхватит
его автоматически. Четыре обязательных блока:

1. **Причина** — что изменение исправляет или добавляет.
2. **Проверки** — какие проверки выполнены и с каким результатом.
3. **Риск** — что может сломаться и какова область затронутого.
4. **Способ отката** — как вернуться к прежнему состоянию.

PR без заполненных блоков не сливается.
